Global variables (`{name}`, not `{_name}` or `{-name}`) are saved to `plugins/NeoSkript/variables.csv` by default. With [native storage](#native-storage) on, they're in `variables.nsv`, and [databases](#databases) can put some or all of them in SQLite or MySQL, as Skript's `databases:` section does. For how scripts use variables, see [variables](/docs/scripts/variables/).

<FileTree>

  - variables.csv saved variables
  - backups/

## Skript's format, both ways

`variables.csv` is in Skript's own format, values and all, byte for byte. NeoSkript reads the file Skript wrote, and Skript can read the file NeoSkript writes, so switching back to Skript keeps your variables. The test harness checks this both ways against a real Skript server, for text, numbers, booleans, timespans, dates, worlds, locations, players, items, vectors, entity types, game modes and more.

A saved value of a type NeoSkript doesn't have yet is kept as it was saved and written back unchanged, so nothing is lost. The startup line counts them: `Loaded 1520 variables in 43 ms (3 kept as saved until NeoSkript supports their types)`.

## When it's saved

- Variables load before scripts, when the server starts.
- Changed variables are saved every `variables.save-interval`, 5 minutes by default, and when the server stops.
- A save writes a temporary file, syncs it to disk and then swaps it in, so a crash or power cut in the middle of a save can't leave a half-written file. Temporary files left by an interrupted save are removed at the next start.

If the server crashes, only the changes since the last save are lost.

`{-name}` variables are never saved, and nor are local variables.

## Backups

NeoSkript backs up `variables.csv` to `backups/` beside it, named as Skript names its backups:

- **Every `backup-interval`**, keeping the newest `backups-to-keep`, as Skript's `backup interval` and `backups to keep`. A server that moved from Skript has exactly what its `config.sk` says, copied as is: with Skript's default config, every 2 hours, keeping every backup (`-1`), and a database that names no backup interval makes none. A new install, or a NeoSkript config from before the `databases` section, gets every 2 hours, keeping 12 (a day's worth). Scheduled backups are named `variables_<time>_scheduled.csv`. Unlike Skript, which counts and removes every file in `backups/`, only that database's scheduled backups are counted and removed: the backups below, made to keep something safe, are never removed automatically. SQLite files are backed up the same way, as a whole, consistent copy even while they're written to. A backup is written as its name with `.copying.tmp` after and renamed once it's whole, so a backup is never half a file; one cut off by a crash is removed at the next start. Saves don't wait for a backup, and when the server stops, a backup still copying is cut off rather than waited for. See [databases](/docs/server/configuration/#databases).
- **The first start after moving from Skript** backs up the copied file before loading it.
- **When some lines can't be read**, for example the last line cut short by a crash under Skript, the file is backed up first. The lines that can't be read are skipped and the rest load, as in Skript. The console lists them with Skript's summary (`1 variable could not be loaded!`, `Affected variables: ...`), and the next save leaves them out; the backup keeps them.

If the file can't be read at all, NeoSkript says so in the console and doesn't save variables until it's fixed, so it never writes an empty file over yours.

<Aside type="caution">
These backups sit beside the file, on the same disk. Back up `plugins/NeoSkript` with the rest of your server too.
</Aside>

## Native storage

For servers with many variables, NeoSkript has its own storage. Turn it on in `config.yml` by setting the `default` database's type to `native`, and restart:

```yaml
databases:
  default:
    type: "native"
    pattern: ".*"
    file: "variables.csv"
```

The variables are then saved in `variables.nsv`, next to where `variables.csv` was (the `file` it names).

- **Faster to load.** 140,000 variables load in under 300 ms, against about 450 to 550 from `variables.csv` (see below), and the file is a third the size. Lists whose names were first saved in any order, like `{firstjoin::%uuid%}`, are sorted once while loading: 600,000 random player UUIDs load in about 1.3 s, where setting them one by one takes 2.4.
- **A save writes only what changed.** Each save adds the variables that changed since the last one to the end of the file, instead of writing every variable again. Now and then, when the file has grown to more than twice what its variables need, a save writes it afresh.
- **A crash can't cut a save in half.** Each save is synced to disk and then committed: its end is written into one of two commit blocks at the start of the file, and synced too. If the server stops before a save is committed, the next start loads every committed save and ignores the rest, however the crash left it. Loading writes nothing, so it works on a full disk; the first save after it backs the file up to `backups/` and writes it afresh. The two commit blocks and the file's identity are each in a 4 KiB block of their own, so a power cut while one is written can't take the others with it.

Values are kept in Skript's own format inside it, as in `variables.csv`, so moving between the two loses nothing, values NeoSkript can't read yet included.

### Snapshots and damage

Each time the file is written afresh, a copy goes to `backups/snapshots/`, and the last 3 are kept, ordered by a counter in the file rather than by their times. Until the next time, that copy is exactly the start of `variables.nsv`. A native file holds up to 2 GiB of variables; a save that would need more is refused, keeping the file as it was, and the console says so. Count on up to about 5 times your variables' size on disk: `variables.nsv` can grow to twice what its variables need before it's written afresh, and each snapshot is about their size.

Committed saves were already on disk, so anything wrong with them is damage, from the disk or something else, not a crash:

- **Damage in what the newest snapshot covers** is repaired from it when the server starts, with the saves since taken from the file. Nothing is lost, and the console says what happened. Each file has a random id that its snapshots carry, so a snapshot is only ever used for its own file.
- **Damage after that** stops the load: NeoSkript says where it is and names the newest snapshot, doesn't load the variables, and never writes over the file. Scripts run without them, and nothing they set is saved; the console says so when the server starts and again when it stops. To load everything up to the last good save, set `recover: true` and restart:

  ```yaml
  variables:
    recover: true
  ```

  NeoSkript first sets `recover` back to `false` in `config.yml`, so it only ever recovers when you ask. If it can't (a read-only or newer `config.yml`), it says so and doesn't recover. Then it backs up the damaged file, loads the saves before the damage, writes a new file, and lists what's lost: the saves from the damage on, and the variables changed by every part of them that can still be read. This works whether the database's `type` is `native` or `csv`, so a damaged `variables.nsv` can also be recovered while switching back. Or restore the file from your own backups instead.

### Switching, and going back

- **To native:** when the server starts with `type: native` and there's no `variables.nsv` yet, NeoSkript copies `variables.csv` to `backups/`, moves its variables into `variables.nsv`, and removes `variables.csv`, so only one file ever holds your variables.
- **Back to CSV:** set `type: csv` and restart. NeoSkript writes `variables.csv` again, from `variables.nsv`, and moves `variables.nsv` to `backups/`. That `variables.csv` is what Skript reads, so this is also the way back to Skript.

Each file is only removed once the new one and the backup are synced to disk, so a power cut during a switch leaves your variables in at least one whole file. While `variables.nsv` exists, it's the file in use. If a `variables.csv` is next to it:

- with the same variables, a switch was cut off, and the next start finishes it;
- older than `variables.nsv`, it's moved to `backups/` unread;
- newer, with different variables, something that doesn't know about `variables.nsv` saved it (an older NeoSkript, or Skript). NeoSkript won't pick one: it says when each was last changed, loads no variables and saves none, until you move the one you don't want out of the folder.

### Before downgrading

NeoSkript versions without native storage, and Skript, only read `variables.csv`. With native storage on, there's no `variables.csv`, so they'd start with no variables. NeoSkript reminds you of this in the console on every start. Before downgrading, or going back to Skript, set `type: csv` and restart once. If you downgrade anyway and the older version saves a `variables.csv`, upgrading again stops at the case above instead of losing either file.

### How fast

The [variable benchmark](https://github.com/xena-studios/neoskript/blob/main/test-harness/README.md) has Skript make 140,000 variables of the kinds servers keep (numbers, texts, booleans, locations and lists), then times loading them when the server starts, as each logs it (median of 3, Paper 26.3):

| | Load | File |
|---|---|---|
| Skript, `variables.csv` | 400 ms | 7.8 MB |
| NeoSkript, `variables.csv` | 489 ms | 7.8 MB |
| NeoSkript, native | 275 ms | 2.5 MB |

Server starts vary with what else the machine is doing (Skript logs tenths of a second): across this and earlier runs, NeoSkript's CSV took 423 to 618 ms and Skript's 400 to 800, while native stayed between 271 and 328, apart from one run on a busy machine.

Saving one changed variable out of those 140,000 appends a few dozen bytes, where `variables.csv` writes all 7.8 MB again.

## Players in variable names

With `variables.player-uuids-in-names: true`, the default, a player in a variable's name is their UUID: `{money::%player%}` is saved as `money::` and the UUID. With `false`, it's their name, which breaks when a player changes it.

This is Skript's `use player UUIDs in variable names`, on by default in Skript too. When you move from Skript, NeoSkript copies the setting from `config.sk`, so the variables Skript saved under names or UUIDs are found. Changing it later doesn't rename saved variables.

## Values that can't be saved

Some values can't go in a file, such as entities. A script that puts one in a global variable gets a warning when it loads, and the variable is gone after a restart. If a save finds values it can't save, the console says how many.

## Databases

The `databases` section of `config.yml` is Skript's `databases:` section from `config.sk`, with the same options, so variables can live in several files and databases. Each variable is saved in the first database, from the top, whose `pattern` matches its whole name, and in no other:

```yaml
databases:
  # Shared with the other servers on the network.
  network:
    type: "mysql"
    pattern: "synced_.*"
    monitor-changes: true
    monitor-interval: "20 seconds"
    host: "db.example.net"
    port: 3306
    user: "minecraft"
    password: "..."
    database: "skript"
    table: "variables21"
  # Everything else, in variables.csv.
  default:
    type: "csv"
    pattern: ".*"
    file: "variables.csv"
    backup-interval: "2 hours"
    backups-to-keep: 12
```

Every option is in [configuration](/docs/server/configuration/#databases). As in Skript:

- `{-name}` variables are never saved, whatever the patterns say. A variable no pattern matches isn't saved in a file; an SQL database keeps the row it has.
- A variable found in two databases at startup is kept from the lower one, with Skript's warning.
- A variable found in a database it no longer belongs to, after a pattern changed, moves to the one it belongs to. The old database lets go of it only once the new one has saved it.

### SQLite and MySQL

The table is Skript's: `variables21`, with `name`, `type`, `value` and `update_guid`, and on MySQL a `rowid` and Skript's `ucs2` character set. Values are in the same binary format as `variables.csv`. So Skript and NeoSkript can take turns on the same `.db` file or MySQL database, in either direction; the test harness checks this against Skript 2.17.0, items and locations included. A row NeoSkript can't read, such as an addon's type, is kept and written back unchanged.

NeoSkript talks to the database itself, with the SQLite and MySQL drivers Paper and Folia include. Skript needs the [SQLibrary](https://www.curseforge.com/minecraft/bukkit-plugins/sqlibrary) plugin for this, last updated in 2014, and its MySQL support asks for a driver class (`com.mysql.jdbc.jdbc2.optional.MysqlDataSource`) that Paper's MySQL driver no longer has, so on current Paper, Skript's MySQL storage doesn't start. NeoSkript needs neither.

Changes are written within a second or so, on a thread of their own, never the server's: only what changed since the last write, in one transaction.

### Sharing variables between servers

With `monitor-changes: true`, each server reads the others' changes from the database every `monitor-interval`, through Skript's `update_guid`. Use the same `pattern`, `monitor-changes` and `monitor-interval` on every server that shares a database, as Skript says.

Each server writes its own changes before it reads the others', and a change it hasn't been able to write yet is never replaced by another server's: it's written over theirs, as Skript writes each change at once. Changes are read by rowid, and the last check's rows are read again, so a write that commits a little late is still seen. A write held up for longer than one `monitor-interval`, on a busy database, can still be missed by the other servers until the next restart, as in Skript.

Unlike Skript, a variable deleted on one server is deleted on the others: with `monitor-changes` on, a deletion is written as a row without a value, which Skript ignores when it reads, and such rows are removed a while later, as Skript removes them. Skript servers on the same database see NeoSkript's changes, but not its deletions.

Also unlike Skript, two servers changing one variable at once don't lose a change. **This applies to every database with `monitor-changes: true`, not only network variables.** Each write checks the rows it writes against what the server last saw of them (locking them, on MySQL, until it's done). Where another server wrote one since:

- **Numbers only added to or taken from** on this server since its last write (`add` and `remove` with numbers, nothing else) have this server's additions added to the other's value: `add 1 to {x}` on two servers at once adds 2. NeoSkript knows which changes were only additions, rather than guessing from the numbers: a `set`, even to the same value, followed by an `add` is a set.
- **A value added to a list** at an index the other server filled first moves to the next free one, so both are kept. Which value ends up at which index isn't guaranteed to be the same as the order they were added on the servers, and a list's order across servers isn't guaranteed at all: sort it where order matters.
- **Anything else is the last write's**, as in Skript: a `set`, a `delete`, a whole list set, sorted or deleted. A deletion racing an addition on another server ends either deleted (if the deletion is written last) or at just the other server's addition (if the addition is: it's added to nothing).

This covers an outage too: additions made on every server while the database was down all count once it's back. A write whose answer the database never sent back (the connection dropped just after it committed) is counted once: each write also updates a row of the server's own, `-neoskript-write::<update_guid>`, with no value and the write's number, and once the database is back that row says for sure whether the write committed. Skript and NeoSkript both skip rows without a value when they load, so it's never a variable, and it goes when the server stops. A Skript server watching the same table tidies such rows away; if it has, NeoSkript checks the rows for the exact values it sent instead. To keep Skript's rule exactly, set `merge-changes: false` on the database: the last write wins, whatever it was.

[NeoSkript Proxy](/docs/addons/proxy/#network-variables) builds `{network::...}` variables on this, and tells the other servers about each write so they don't wait for `monitor-interval`.

### When a database is down

NeoSkript never stalls the server waiting for a database, never writes to one it didn't load, and doesn't lose changes while the server runs:

- **Down when the server starts:** NeoSkript waits at most 10 seconds for each database. Then the other databases load and scripts run, but this database's variables aren't loaded, and nothing is written to it. Its pattern still owns its variables, so they aren't saved anywhere else by mistake. NeoSkript keeps trying in the background, and when the database answers, it loads its variables: only the ones its pattern owns, and never one another database loaded when the server started, so the order rule above still holds. Until then, scripts find that database's variables empty, which never happens in Skript, since it waits for every database before scripts load. When the database loads, its saved values replace what scripts set meanwhile for names it has, and the console lists them; names it doesn't have keep what scripts set. While it's never been reached, what scripts set for it is kept in `pending/` every 30 seconds, so even a crash doesn't lose it, and the next start puts it back in memory before scripts run.
- **Drops out later:** writes stop, and the console says so once, then every 5 minutes with how many changes are waiting. Nothing is queued: NeoSkript works out what changed again each time it tries, so an outage of any length costs no extra memory. When the database is back, everything that changed is written and the console says so.
- **Down when the server stops:** the changes that couldn't be written are kept in `plugins/NeoSkript/pending/<database>-<id>.pending.csv`, in Skript's CSV format, and written at the next start. They're also kept every 30 seconds while it's down. If the database was never reached at all, the variables scripts set for it are kept in `<database>-<id>.unloaded.csv`, and the next start adds the ones the database doesn't have. The id comes from the database's type, where it is and its table, which the file also records: a file kept for a database that has since moved, or for another table, isn't applied, but set aside with a warning. A kept change is only applied if the database's row for it is as this server last saw it: if anything wrote the row since, another server or an earlier start, the database's value is kept, and the console says how many were left out.
- **The server stops:** every database closes at once, and the server waits for them together, about 20 seconds at most. One that doesn't answer in time keeps what it couldn't write in `pending/`, and the console says so.
- **No driver:** if the server doesn't have the SQLite or MySQL driver (Paper and Folia do), the console says so once, and it isn't tried again.
- **A row the database refuses** (a name longer than MySQL's 380 characters, a character `ucs2` can't hold) doesn't hold up the rest: the console names it, and it keeps its value until the server stops.
- **A locked SQLite file**, held by another program, waits 5 seconds, then is tried again later like a database that's down. So does a full disk.

`/sk info` shows each database: connected and how many variables it has, down since when, why, and how many changes are waiting, or not reached yet. A password is never shown, in the console or `/sk info`.
